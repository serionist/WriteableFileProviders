# Ship 2027.1.0 with the five additions a consumer needs before it pins the packages

A consumer audited 2027.0.0 (`c95e123`) for its file store. The ranges, the atomic create-only, the signed links and
the gateway hold. It waits for a 2027.1.0 with five additions, each an issue under the epic #64. This plan spans six
PRs, one per step, so after its first merge each step's PR updates its progress log and its decisions
([docs/plans/README.md](README.md)).

## Goal

2027.1.0 of every package is on nuget.org with:

1. **#62:** an `IfNotExists` write that finds a file there throws `FileAlreadyExistsException`, which derives from
   `PreconditionFailedException`. Every provider throws it (D2).
2. **#60:** a conformance test races `IfNotExists` writers on one path, with a small file and with one large enough
   to take the S3 multipart and Azure block-list paths. It is green in CI on the local disk, Azurite and MinIO.
3. **#59:** the gateway's Data Protection root purpose is an option, `WriteableFileProviders.Gateway.v1` by default.
4. **#61:** Physical can refuse links inside its root (an option, off by default), and can delete the temp files a
   crashed write leaves behind (a method).
5. **#63:** a caller can give any provider it builds its clock, and every time a provider computes comes from it.

2027.x adds features and fixes and breaks nothing ([versioning](../guide/versioning.md)). Every addition is new API
or opt-in. The one change an existing caller can see is the exception's new subtype (Compatibility).

**In scope:** the five issues, their tests and docs, the changelog, and the release.

**Out of scope:**

- Refusing reparse points that aren't links (cloud placeholders, deduplicated files, container image layers), hard
  links and bind mounts (D4).
- A link refusal that is atomic with the operation (D4).
- Redeeming tokens issued under an earlier gateway purpose after the purpose changes (D3).
- A clock through the options or picked up from DI (D5).
- A clock for a provider built from configuration or JSON, by the serializer or
  `AddWriteableFileProvider(configuration)`: it keeps the system clock. An app gives one a clock by building it in code
  (D5).
- Making an unconditional append agree across providers when another writer creates the file meanwhile (D2, #65).
- The live suites. Their accounts come later. Each step's PR says they didn't run.

## Decisions

Decided while planning. The maintainer's approval of this plan approves them.

- **D1. The create-only exception is a new type: `FileAlreadyExistsException : PreconditionFailedException`.**
  `FileExistsException` (a copy's or a move's destination exists) stays as it is. The name is Java NIO's for the same
  failure. The XML docs of both types, and the errors guide, say which is which.
  - *Rejected: rebasing `FileExistsException` onto `PreconditionFailedException`.* A `catch
    (PreconditionFailedException)` around a copy or a move would start catching destination conflicts. Code that
    catches `PreconditionFailedException` before `FileExistsException` would stop compiling (CS0160).
  - *Rejected: a reason property on `PreconditionFailedException`.* Catch clauses match types.
- **D2. The promise is `IfNotExists`.** On every provider, an `IfNotExists` write that finds a file there throws
  `FileAlreadyExistsException`, and only a file counts: a folder at the path gets the store's own answer (D8).
  - An unconditional append to a missing file that another writer creates meanwhile differs today, and stays as it
    is. Physical and the append-by-rewrite providers (S3, MinIO, GCS, Box, SharePoint) refuse it, and since their
    refusal is a create-only failure, it raises the new type. Azure re-reads and appends after the new content, as it
    does after any concurrent change (`Append_CreatingRacesWithAnotherCreator` pins it).
  - Both keep the other writer's content. `providers.md` records the difference, and issue #65 tracks making appends
    agree, which would change behaviour and so waits for a decision of its own.
  - Decided by @serionist on 2026-10-12 (plan review P1).
- **D3. The gateway purpose is `WriteableFileProviderGatewayOptions.DataProtectionPurpose`.** It is read once, at
  startup. Changing it ends every URL issued under the old one, and the docs say so. There is no list of earlier
  purposes to keep redeeming: the request doesn't need one, and the option can add one later without a break.
- **D4. `RefuseLinks` refuses links, not every reparse point.** A link is an entry .NET reports a `LinkTarget` for: a
  symbolic link, a junction, a mount point.
  - *Departure from the request,* which says "or other reparse point". Cloud placeholders (OneDrive), deduplicated
    files and Windows container layers are reparse points that hold the entry's own content where it is. Refusing
    them would refuse every OneDrive-synced folder and every file of a Windows container image.
  - *Not atomic.* The check walks the path before the member acts, so a process that can make links inside the root
    can swap one in between. The docs say so.
  - *Not refused:* hard links and bind mounts, which the file system doesn't show as links.
- **D5. The clock is `public TimeProvider Clock { get; init; }` on `WriteableFileProvider<TOptions>`.** It sets the
  protected `TimeProvider` and works with every constructor: `new X(options) { Clock = fake }`. With DI, it goes
  through the factory overload.
  - *Rejected: a `(options, TimeProvider)` overload of each constructor.* That is 13 public constructors across seven
    providers for one setting.
  - *Rejected: a `TimeProvider` on the options.* Options are the configuration shape. The serializer would have to
    skip it, and the configuration binder's source generator warns on a property it can't bind, which fails an AOT
    app that binds our options with warnings as errors.
  - *Rejected: `AddWriteableFileProvider` picking up the app's `TimeProvider` service.* That would silently change
    the clock of an app that registered a fake one for its own tests.
  - *Rejected: a public `set`.* It wouldn't reach a provider built from configuration either (`Clock` isn't on
    `IWriteableFileProvider`, so that still takes a cast). Swapped while the provider runs, it would mix two clocks in
    Box's and SharePoint's timed waits and in Azure's refusal windows and key cache. `init` sets it once.
  - *A provider built from configuration keeps the system clock.* A serializer overload that takes a clock can come in
    a later minor, under a name of its own so `FromConfiguration(section, null)` stays unambiguous.
  - Either accessor is final within 2027.x: `init` and `set` compile to different setters. Package validation against
    2027.0.0 wouldn't notice a flip, since `Clock` isn't in 2027.0.0, so the XML doc says so.
  - Decided by @serionist on 2026-10-12 (plan review P3).
- **D6. A store that signs on its own clock keeps the URL's duration.** S3 and MinIO: the AWS SDK stamps `X-Amz-Date`
  from its own skew-corrected clock, and a provider can't set that per client. So the SDK gets the asked duration,
  and the provider's clock gives `ExpiresOn` and the credential-expiry check. With the system clock this is what
  happens today.
  - Azure (already) and GCS (new, through `UrlSigner.WithClock`) sign absolute times from the provider's clock. A
    clock set back gives URLs the store refuses as expired, which is how a test checks expiry without waiting.
  - *Departure from the request:* the S3 test that waits (`SignedUrls_AreCheckedByTheServer`) checks that the server
    refuses an expired URL. The server judges by its own clock, which no client clock moves. So it keeps its bounded
    wait (at most a minute, one to two seconds in practice), and offline tests with a fake clock cover S3's and
    MinIO's `ExpiresOn` and credential check.
- **D7. Steps run one after another in this session, and each PR merges before the next starts.** They share
  `CHANGELOG.md` and this plan.
- **D8. A folder at the path of an `IfNotExists` write gets the store's own answer, as a write without conditions
  does.** That is `IOException` where folders are real, and the file written beside it where folders are prefixes
  (`Write_AFileAtAFolderPath`).
  - Today the base check (`Core.cs:419`) and the append check (`:340`) count a folder as an existing file. So an
    `IfNotExists` write at a folder path throws "already exists" on the stores whose conditions are checked, throws
    `IOException` on Physical and on Box with `If-Match`, and writes beside it on AWS, Azure and GCS.
  - The append rewrite at a folder path also drops the create-only condition (`:360-361`). So on S3, MinIO and GCS, a
    file created at that path at the same moment is silently replaced.
  - Step 1 fixes both: only a file counts as existing, and the rewrite's conditions come from whether a file is
    there. SharePoint's 409 under `IfNotExists` looks the item up: a folder gives `IOException`, a file
    `FileAlreadyExistsException`.
  - It's a fix, and the changelog says what moves. Decided by @serionist on 2026-10-12 (plan review P4).
- **D9. Physical takes a new name without a placeholder on Linux and macOS.**
  - Today `RenameToNew` creates an empty file at the name (`FileMode.CreateNew`), then renames the content over it.
    A write that looks at the path in between sees an empty file. An append then appends to it, its version check
    matches the placeholder, and it reports success, until the first writer's rename replaces it: the append is lost.
    Or the version check catches the rename, and it throws the base type.
  - Step 2 takes the name with `link(temp, target)`, then `unlink(temp)`, through `LibraryImport` (AOT-safe). `link`
    fails with `EEXIST` when anything has the name, which is atomic and leaves no placeholder.
  - **Only `CommitAsync`, where it takes a new name, takes this path:** a write with `IfNotExists`, an append to a
    missing file, a copy. An overwrite, an append to an existing file and a local stream's commit replace by rename and
    never had the placeholder. A move keeps today's rename, and the class remarks keep the empty-file moment for a
    move's destination. Through `link`, a move would go wrong four ways:
    - macOS's `link` follows a symbolic link at the source, so moving a link would hard-link its target;
    - a crash would leave the caller's file under two names, neither of them a temp name the sweep removes;
    - a source folder that refuses the `unlink` (sticky, read-only) would leave the move half-done, where today's rename
      is refused whole;
    - undoing it by unlinking the destination could remove another writer's content.
  - **Any failure of `link` other than `EEXIST` falls back** to today's placeholder path, which raises today's
    exceptions. `EPERM` and `ENOTSUP` are the file systems without hard links; `ENOSYS` (FUSE), `EACCES` (an LSM that
    denies links) and `ENOENT` (a vanished temp file) fall back too. The check compares against `EEXIST` alone, 17 on
    both systems, so values that differ between Linux and macOS (`ENOTSUP`, `ENOSYS`) never need naming. The docs say
    where the window remains.
  - **Once `link` succeeds, the write is done.** A failed `unlink(temp)` is ignored: the file is in place, and the temp
    name is hidden and swept. That includes a sweep that removed it between the two calls. So a crash between the two
    calls leaves the full file plus a hidden temp name, where today a crash at that moment leaves an empty file.
  - **The call:**
    - only on Linux and macOS, chosen by `OperatingSystem.IsLinux() || OperatingSystem.IsMacOS()` through an internal
      init seam. The seam also injects a refusal for the fallback's test, and on Windows the tests that take names
      the Linux way run the fallback;
    - `[LibraryImport("libc", StringMarshalling = StringMarshalling.Utf8, SetLastError = true)]`, read with
      `Marshal.GetLastPInvokeError()`;
    - `EEXIST` becomes an `IOException` naming the target, never the temp name, handed to the caller's `exists`, as
      the exclusive create's is today. Step 2 updates `TakeNewNames`' comment, and adds a case with the injected
      refusal so the fallback's race refusal still runs on Linux;
    - Physical's project gains `AllowUnsafeBlocks`, which the generated code needs (SYSLIB1062). It is the repo's first
      P/Invoke, and the AOT job reaches it on Linux through the app's copy.
  - Windows already renames without replacing.
  - A fix, with a changelog line. Decided by @serionist on 2026-10-12 (plan review N3; R1 scoped to writes and
    copies).

## Design

### FileAlreadyExistsException (#62)

```csharp
/// A write with UpdateFileOptions.IfNotExists found a file at the path; nothing was written. A provider that refuses an
/// append to a missing file that another writer created meanwhile throws it too (see the provider). Not
/// FileExistsException, which a copy or a move throws when its destination exists.
public class FileAlreadyExistsException : PreconditionFailedException
{
    public FileAlreadyExistsException();                                   // "The file already exists."
    public FileAlreadyExistsException(string? message);
    public FileAlreadyExistsException(string? message, Exception? innerException);
}
```

Every place that throws `PreconditionFailedException("The file '…' already exists.")` throws the new type:

| Where | What |
|---|---|
| Common | The base class's check when the store's conditions aren't atomic (`UpdateWithPreconditionsAsync`), and `AppendByRewriteAsync`. Both count only a file (D8): `info.Exists && !info.IsDirectory`. The rewrite's conditions come from whether a file is there (`IfMatch` its ETag, else `IfNotExists`), so an append at a folder path stays create-only. |
| Physical | `AlreadyExists`: the stat before the write, and the atomic create. |
| Azure Blob | `PreconditionFailed` for `IfNotExists` (a 409 or 412, or `InvalidBlockList` after a winner's commit), `CheckReplace`, and an `IfNotExists` append that loses its create (`Writes.cs:227-228`). An unconditional append that loses its create appends after the winner, as today (D2). (`Kept`, which re-wraps a failure that lost the old content, never sees a create-only failure: `CheckReplace` refuses an existing blob before anything is destroyed.) |
| S3, MinIO | `S3Core.WriteAsync`: a 412. On the 409 `ConditionalRequestConflict`, which AWS also answers when a concurrent operation such as a delete conflicts, a `HEAD` decides: a file there gives the subtype, none the base type, whose message says a concurrent operation conflicted and the write can be retried (plan review P14). |
| GCS | The generation-0 condition failure. |
| Box | The name conflict of an upload. |
| SharePoint | The `fail` conflict behaviour (409), on a simple upload and on an upload session. Under `IfNotExists` the 409 looks the item up: a file gives the subtype, a folder `IOException`, as a write without conditions gives (D8). Nothing found (deleted meanwhile), or a lookup that fails, gives the base type, whose message says a concurrent operation conflicted and the write can be retried, as S3's does. All three sites: the simple upload, the session's creation and the session's commit. |
| Tests | `InMemoryFileProvider`, the reference provider. Today it throws nothing of its own: it leans on the base class's check, which isn't atomic, and its write overwrites under its lock whatever the conditions. Step 1 adds the store's own check under that lock: an existing entry with `IfNotExists` throws `FileAlreadyExistsException`; an `IfMatch` that differs, or has no entry, throws `PreconditionFailedException`. `SupportsAtomicPreconditions` stays false, as SharePoint's and Box's checked modes are, so the reference fixtures keep exercising the base class's check, and the store's check settles a race. |

- **The default `CopyCoreAsync`** writes the destination with `IfNotExists`. It turns a lost race into
  `FileExistsException`, as `CopyAsync` documents. Today it leaks `PreconditionFailedException`, so this is a fix.
  - It catches only `FileAlreadyExistsException`: the source stream can throw the base type (Azure's pinned read, for
    one), and that must pass as it is.
  - The default `MoveCoreAsync` copies through it, so a move gets the fix too, and both are tested.
  - Physical's copy already does it.
- **The gateway** still answers 412 to a create URL whose file exists: it catches the base type.
- **Nothing maps the base type to the subtype.** With `IfNotExists` set, a `PreconditionFailedException` can still
  come from the caller's own content stream (one provider's pinned read, copied into another), so each provider
  throws the subtype where it knows the cause.

### The race test (#60)

The test goes in `ProviderConformanceTests`, so every fixture runs it, the live suites included:

- **`Write_IfNotExistsRaceHasOneWinner`:** 8 writers, each with its own content, start together. Each task awaits one
  `TaskCompletionSource`, then calls `UpdateFileAsync` with `IfNotExists`. Then:
  - exactly one write completes;
  - each of the other 7 throws `FileAlreadyExistsException`;
  - the file reads back exactly the winner's bytes;
  - `LocalTempFolder` holds no `.wfp-*.tmp`.
- **`Write_IfNotExistsRaceHasOneWinner_Large`:** the same with 4 writers at `LargeRaceFileSize`, compared by SHA-256.
  - The new knob `LargeRaceFileSize` defaults to `Math.Min(LargeFileSize, 32 MiB)`. Each fixture's `LargeFileSize`
    already crosses its store's threshold as the fixture sets it. The S3 and MinIO fixtures upload in 5 MiB parts, so 11
    MiB is a three-part multipart upload. The plain Azurite fixture stages 1 MiB blocks, so 16 MiB is a 16-block list.
    The strict one caps the list at 6 blocks, so there it is 6 blocks of about 2.7 MiB, still a block list. GCS uses 22
    MiB. With the providers' defaults (8 MiB parts and blocks) a write above 8 MiB takes the same paths.
  - The hash check proves no loser's staged blocks or parts end up in the winner's file. On Azure, losers stage under
    random block ids, and the winner's commit drops them.
- **Two new knobs, both true by default:** `RefusesConcurrentCreates`, and `RefusesConcurrentLargeCreates` (which
  defaults to the first). False makes that size's test inconclusive, for an emulator that can't settle the race, and
  the fixture's comment names the emulator and why. Two knobs, so an emulator that fails only the large race still
  runs the small one.
  - Neither is ever false for Physical, Azurite or MinIO. If one of those fails, that is a provider bug, which step 2
    fixes, or an emulator bug, which goes to the maintainer before going on.
  - The large race is also inconclusive where `FailedLargeWriteKeepsOldContent` is false. That is S3Mock 5.2.3: a
    loser aborts its multipart upload (`S3Core.Writes.cs`), and S3Mock then deletes the object, the winner's file
    included. Whether S3Mock settles the small race (toward a named endpoint the provider checks first, then sends
    `If-None-Match`) step 2 finds out.
- **The writers start together on the thread pool.** Each starts with `Task.Run` and awaits a gate, a
  `TaskCompletionSource` made with `TaskCreationOptions.RunContinuationsAsynchronously`, which the test opens once
  every writer has arrived (a countdown completes a second task source). Without the option, `SetResult` would run the
  first writer inline on the test thread.
- **Assertions hold under any interleaving** for a provider whose store settles the condition. Writers the scheduler
  happens to serialize must still give one winner, so the test can under-exercise the race but never fail falsely.
  The in-memory provider settles it only once step 1 adds its own check, which is why step 1 comes first.

### The gateway purpose (#59)

- `WriteableFileProviderGatewayOptions.DataProtectionPurpose`, a `string`, defaults to
  `"WriteableFileProviders.Gateway.v1"`.
- The validator refuses null, empty or whitespace when the app starts.
- `GatewayTokenCodec` takes `IOptions<WriteableFileProviderGatewayOptions>` and builds the chain `{purpose}`, then the
  provider key when there is one, then the access. That is today's chain with the root from the option.
- The golden tokens keep redeeming under the default.

### Physical: links and leftovers (#61)

**`PhysicalFileProviderOptions.RefuseLinks`** is a `bool`, false by default. When it is true:

- Every member refuses, with `ArgumentException`, a path any of whose entries under the root is a link. That includes
  the entry it names, and both ends of a move or a copy. `FullPath` refuses a path outside the root, or an 8.3 short
  name, the same way. The errors guide's row ("a path … the provider refuses") already covers it.
- Listings leave links out, so everything listed can be read back.
- `Watch` is unchanged. Its watcher can walk into a linked folder, so a token can fire for a change behind a link,
  even outside the root. It reports only that something changed, never what or the content. The README and the XML
  doc say so; step 4 checks the watcher's behaviour on both systems before writing it down.
- The root itself, and the folders above it, may be links.
- The check stats each entry from the root down (one `lstat` per segment) before the member acts (D4).

**`WriteablePhysicalFileProvider.DeleteTempFilesAsync(TimeSpan olderThan, CancellationToken cancellationToken =
default)`** returns `Task<int>`.

- It deletes, under the root, every file whose name is exactly a write's temp name. That is `IsTempFile`: `.wfp-`,
  32 lowercase hex digits, `.tmp`. So `.wfp-notes.tmp` is never touched, and neither is Common's
  `.wfp-rename-<guid>.tmp`, which holds a file's content.
- It deletes only temp files whose last write is older than `olderThan` on the provider's clock, and returns how many
  it deleted.
- It walks every folder and doesn't go into a link, whatever `RefuseLinks` says. As with a recursive listing, the
  check runs before each folder is walked, not atomically with the walk. A process that can make links inside the
  root could swap one in and steer the sweep into a folder elsewhere. There it deletes only files named exactly like a
  write's temp file and older than the age. The README and the XML doc say so (plan review P11).
- A temp file it can't delete is skipped: a write still has it open on Windows, or the system refuses. A folder it
  can't list throws `UnauthorizedAccessException`, as a listing does.
- A negative `olderThan` throws `ArgumentOutOfRangeException`. A missing root returns 0.
- **A write still in progress.** Its temp file's last write moves only when bytes are flushed. An age longer than the
  longest write is safe, since the last write is never before the temp file's creation.
  - A write whose source stalls longer than the age loses its temp file on Linux and macOS, and fails with
    `IOException` naming the path under the root, never the temp file. It leaves the file as it was.
  - Without a change it would fail with `FileNotFoundException` naming the temp file, which the contract reads as
    "doesn't exist". So `CommitAsync` turns a failure of the stamp or the rename whose temp file is gone into that
    `IOException`.
  - On Windows, the open write refuses the delete, and the sweep skips it.
- **Why a method and not a construction option:** a constructor does no I/O (the base class's rule), and the app
  picks when to run it: at startup, or on a timer.

### The clock (#63)

```csharp
public TimeProvider Clock { get => TimeProvider; init => TimeProvider = value ?? throw new ArgumentNullException(nameof(value)); }
```

- It replaces Physical's and Azure's `internal Clock` hooks. Their tests keep the initializer syntax, and the Azure
  tests that set it after construction move to the initializer.
- `writing-a-provider.md` tells a provider to read `TimeProvider` when it needs the time, never to capture it in its
  constructor, which runs before the initializer.

What reads it, provider by provider:

| Provider | Reads the clock for |
|---|---|
| Physical | Write stamps (today); the age in `DeleteTempFilesAsync` (new). |
| Azure Blob | SAS start and expiry; the user delegation key's cache and requests; how long a refused server copy is remembered. All today. |
| S3, MinIO | `ExpiresOn` and the credential-expiry check (today). The SDK gets the duration: its `Expires` becomes the system's now + `Validity`, where today it is the clock's now + `Validity`: the same on the system clock (D6). |
| GCS | The URL signer, through `UrlSigner.WithClock` and a small Gax `IClock` that reads the provider's `TimeProvider` on every call, so `X-Goog-Date` and `ExpiresOn` come from it (new). Google.Cloud.Storage.V1 5.0.0 has `WithClock(IClock)`. The given-client constructor builds its signer before the initializer runs, which is why the `IClock` reads the property each time rather than holding a clock. |
| Box | Download URL `ExpiresOn` (today). The waits: polling for a download that isn't ready and for an upload session, through `Task.Delay(…, TimeProvider)` and `GetElapsedTime` (today). |
| SharePoint | The waits of a copy's polling (today). |
| Gateway | Unchanged: its clock is the app's `TimeProvider` service. |

- **The clock times the waits too,** on Box and SharePoint. A test that gives them a manual fake clock must advance it
  (or let it advance by itself), or a wait never ends. The docs say so.
- **A third-party provider with a member named `Clock`** of its own (as Physical and Azure have today, internally)
  gets warning CS0108 for hiding the new one, an error with warnings as errors. That is the usual cost of any
  member a base class gains; the changelog names it.

## Compatibility

- **New public API, additions only:**
  - `FileAlreadyExistsException`;
  - `WriteableFileProvider<TOptions>.Clock`;
  - `WriteablePhysicalFileProvider.DeleteTempFilesAsync`;
  - `PhysicalFileProviderOptions.RefuseLinks`;
  - `WriteableFileProviderGatewayOptions.DataProtectionPurpose`.

  Package validation against 2027.0.0 passes additions.
- **One-way doors (AGENTS.md):**
  - *The Common API:* additions, a new exception among them, which AGENTS.md's list gains.
  - *The configuration shape:* one new Physical key, false by default. Every earlier input reads as before. `ToJson`
    writes it only when it is true (`[JsonIgnore(Condition = WhenWritingDefault)]`, as Minio's 2027 options do), so
    a default Physical provider keeps its three keys.
    - A 2027.0 reader given `RefuseLinks: true`, from JSON or configuration, builds the provider and drops the key
      without an error: both readers skip keys the options class lacks, and `Lenient.Minio.json` pins that.
    - So rolling back to 2027.0, or deploying the configuration ahead of 2027.1, follows links again. 2027.1 can't
      make an older reader refuse it.
    - The changelog, the Physical README and the XML doc say so, and `dependency-injection.md` says a reader ignores
      keys it doesn't know (plan review P8).
  - *The gateway's URLs:* the root purpose becomes an option, and the default is today's, which the golden tokens pin.
    AGENTS.md's entry says it is configurable. The maintainers' agreement is recorded on #59 before step 3 merges.
- **Behaviour an existing caller can see:**
  - *Create-only failures are the subtype.* `catch (PreconditionFailedException)` still catches them. Code that checks
    the exact type sees the subtype: `GetType() == typeof(PreconditionFailedException)`, or MSTest's `ThrowsExactly`.
    The changelog says so.
  - *The default `CopyCoreAsync`'s lost destination race throws `FileExistsException`,* as `CopyAsync` documents,
    instead of `PreconditionFailedException`. It's a fix. None of the seven providers takes the default copy; the
    in-memory provider and third-party providers may.
  - *An `IfNotExists` write or append at a folder path* (D8), a fix:
    - Box without `If-Match` (as shipped), SharePoint and the in-memory provider throw `IOException` instead of
      `PreconditionFailedException`, for a write or an append; Box with `If-Match`, for an append (its write already
      throws `IOException`).
    - MinIO, and S3 toward a named endpoint, write the file beside the folder, as AWS already does, for both.
    - AWS and GCS do the same for an `IfNotExists` append, which refused until now (their overwrite already wrote
      beside).
    - Physical and Azure are unchanged.
    - A plain append there stays create-only, where on S3, MinIO and GCS it could replace a file created at that
      moment.
    - A gateway create URL at a folder path answers 201 or 500 where it answered 412.
    - The changelog's Fixed entry lists the same.
  - *S3, MinIO and GCS URLs* are unchanged on the system clock, the only clock a caller could give before.
  - *Physical on Linux and macOS* no longer shows an empty file at a new name while a write or a copy takes it (D9),
    except where the system refuses a hard link; a move's destination still does. A crash at that moment leaves the
    full file and a hidden temp name, where it left an empty file. A fix.
- **Third-party providers** keep building, unless one declares a member named `Clock`, which now hides the base
  class's (CS0108, an error with warnings as errors). To meet the contract they throw `FileAlreadyExistsException`
  where they throw `PreconditionFailedException` for a file that exists (the guide). The base class's own checks
  already do.
- **Migration guide:** nothing to add. There's no break.

## Steps

Each step is one PR from a branch `<issue>-<slug>` off `origin/main`, through `review-code` and `finish-work`. Each
