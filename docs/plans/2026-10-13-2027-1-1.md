# Ship 2027.1.1 with appends that end alike on every provider and a Physical folder delete no link can steer

2027.1.0 left two follow-ups open on purpose: #65, an unconditional append that ends one way on Azure Blob and another
everywhere else when another writer gets there first, and #70, a Physical folder delete that a link swapped in while it
runs can steer outside the root. Both are fixes, so they ship as a patch, 2027.1.1
([versioning](../guide/versioning.md)). This plan spans four PRs, one per step; after its first merge each step's PR
updates its progress log and its decisions ([docs/plans/README.md](README.md)).

## Goal

2027.1.1 of every package is on nuget.org with:

1. **#65:** an append with no condition of the caller's ends the same way on every provider when another writer changes
   or creates the file between the provider's read and its write: the provider reads the file again and appends after
   what is there now, up to five attempts in all, then throws `PreconditionFailedException`. Azure Blob does this today;
   Physical and the providers that append by rewriting (`AppendByRewriteAsync`: S3, MinIO, Google Cloud Storage, Box,
   SharePoint, the in-memory provider, and any third-party provider that calls it) throw at the first conflict.
2. **#70:** Physical deletes a folder through handles: it never goes into a link inside the folder, even one swapped in
   while it runs, and with `RefuseLinks` it also walks down from the root without following one. On Linux and macOS
   through `openat` and `unlinkat`, on Windows through `NtCreateFile` relative to the folder's handle and a delete by
   handle.

**In scope:** the two issues, their tests and docs, two CI jobs that run Physical's tests on macOS and on Linux on Arm
(D6), the changelog, and the release.

**Out of scope:**

- A race test of appends to an existing file. The staged conformance test (`Write_ConcurrentAppendIsNeverLost`)
  exercises the retry on every provider that can detect the staged write; a real race would need a new capability for
  the stores whose `IfMatch` is only checked (Physical, Box as it ships, S3Mock).
- Making `IfMatch` atomic where it is checked (Physical, Box as it ships, SharePoint, MinIO releases without conditional
  writes): an append there can still lose a write that lands between the check and the rewrite, as today.
- Telling a lost answer from a real conflict (Risks, P10): no store gives a way that doesn't also drop one of two
  identical appends.
- Making Physical's other members atomic with the `RefuseLinks` check. A write, a read, a move, a copy or a file delete
  still checks the path just before it acts, as the 2027.1 docs say; #70 is about the folder delete, which walked a whole
  tree.
- Listing a folder through its handle (D4).
- A delay between attempts. Azure retries at once; so do the others.
- The live suites. Their accounts come later. Each step's PR says they didn't run.

## Decisions

Decided while planning. The maintainer's approval of this plan approves them.

- **D1. An append with no condition retries, on every provider (#65; the maintainer's choice, 2026-10-13).** After a
  concurrent change or create, the provider reads the file again and appends after what is there now: up to five
  attempts in all (Azure's `MaxAttempts`), then `PreconditionFailedException`, the base type whatever the last conflict
  was, with Azure's message ("kept changing while it was appended to; nothing was appended after 5 attempts") and the
  last conflict inside. A caller's own `IfMatch` or `IfNotExists` still fails at once, as on Azure: the caller asked for
  that version, or for nothing to be there. A file deleted between the read and the write counts as a change too: the
  next attempt creates it, as Azure does. A folder that takes the name gets the store's answer, unretried. Only the
  provider's own conflict signals go round again (P3): an exception from the caller's stream, whatever its type (a
  pinned read from another provider throws `PreconditionFailedException`), ends the append at once.
  - *Rejected: retry only the create race.* An existing file's conflict would still end differently (Azure retries,
    the others throw at once), so "one meaning" would hold for one case only.
  - *Rejected: Azure refuses.* Azure's appends would get less robust, and a caller that gave no condition would get a
    create-only error.
- **D2. The caller's stream is read once, and a retry costs nothing until it happens (P4).**
  - **`AppendByRewriteAsync`** reads the file, then the caller's stream, into its temp file, as today, and remembers
    where the caller's bytes start. A retry makes a new temp file of the file as it is now, then copies the previous
    temp file from that offset, or the caller's stream while no temp file holds its bytes: no spool, no extra copy
    without a conflict, and nothing in the system temp folder that isn't there today. Reading the file before the caller's stream keeps the order the staged tests rely on (the write
    they stage lands after the read, so the retry is what they exercise).
  - **Physical** deletes its commit temp file when the commit fails, so it copies the caller's stream into a spool of
    its own once the append's early refusals have passed and before the file is opened (N2): a hidden
    `.wfp-<guid>.tmp` in the target's folder, deleted when the append ends; on Linux and macOS private to the process's
    user (`0600`, set as it is created, as `CommitAsync` sets its temp file's mode, U1); on Windows with the folder's permissions, as the commit's temp file has there. Listings hide it and
    `DeleteTempFilesAsync` sweeps one a crash leaves, as for every temp file of a write, so an append needs nothing
    outside the root (N8). Each attempt rewinds the spool and copies it after the file. The appended bytes are written
    twice locally (Risks).
- **D3. A folder delete acts only through handles (#70).** The walk opens each entry relative to its folder's handle
  without following a link, and removes it relative to that handle, or through its own handle on Windows:
  - **Linux:** `openat(folder, name, O_PATH | O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC)` succeeds only on a real folder.
    `ENOTDIR` (or `ELOOP`) means a file or a link, which `readlinkat(folder, name, buffer, 1)` tells apart (a link
    answers; anything else is `EINVAL`), with no structure layouts (P6). A file or a link is removed with
    `unlinkat(folder, name, 0)`; a folder is emptied, then removed with `unlinkat(folder, name, AT_REMOVEDIR)`. `O_PATH`
    needs no read permission, as `unlinkat` doesn't.
  - **macOS:** the same with `O_RDONLY` for `O_PATH`, which macOS lacks, and the same `readlinkat` after either error,
    since which of the two a link gives there is not something this plan relies on (N5). A folder on the way must be
    readable (Risks).
  - **Windows:** `NtCreateFile` with the folder's handle as its root, `FILE_OPEN_REPARSE_POINT`,
    `FILE_SYNCHRONOUS_IO_NONALERT` and `FILE_OPEN_FOR_BACKUP_INTENT`, for `DELETE | FILE_READ_ATTRIBUTES | SYNCHRONIZE`
    (the attributes query needs `FILE_READ_ATTRIBUTES`; synchronous I/O needs `SYNCHRONIZE`), sharing read, write and
    delete, as .NET's relative opens and `DeleteFile` do (P7). Only the entries the walk removes ask for `DELETE`: the
    folder the walk starts from and, with `RefuseLinks`, each folder on the way are opened for
    `FILE_READ_ATTRIBUTES | SYNCHRONIZE`, so the delete needs no more right on them than today's path delete (R3). `GetFileInformationByHandleEx(FileAttributeTagInfo)`
    gives the attributes and the reparse tag. Each entry is deleted through its own handle with `FileDispositionInfoEx`
    (`FILE_DISPOSITION_FLAG_DELETE | FILE_DISPOSITION_FLAG_POSIX_SEMANTICS`), and where the file system answers
    `ERROR_INVALID_PARAMETER`, `ERROR_NOT_SUPPORTED` or `ERROR_INVALID_FUNCTION`, with `FileDispositionInfo`, as Rust's
    `remove_dir_all` does; any other error is the delete's failure.
  - **What an entry is** is decided in shared code from those raw facts (D7): a folder (the directory attribute, and no
    name-surrogate reparse tag), a link (a name surrogate on Windows; a `readlinkat` answer on Unix),
    something else, or nothing (gone). A link is removed as a link, never entered, as .NET's recursive delete does; on
    Windows that includes junctions, which .NET 10 fails on today (D5).
  - **The start:** without `RefuseLinks`, the folder that holds the target is opened by its path, following links as
    every member does; with it, the walk starts at the root (opened by its path, since the root may be a link) and opens
    each folder on the way without following one. A link found there, swapped in after the check, is refused with the
    same `ArgumentException` as the check's; a file or nothing there means the folder is gone, and the delete returns
    false (P12). The target itself is opened without following: a link there is removed as a link, as today (with
    `RefuseLinks`, refused); a file there, put in its place since the probe, is deleted, since the member deletes what
    the path names (N6); nothing there returns false. `Opening` fires for each folder on the way and for every entry.
  - **The file delete** is unchanged (`File.Delete` on the path), as is what `DeleteAsync` returns: the probe that
    decides between a file, a folder and nothing stays, so a link to nothing still returns false.
  - *Rejected: holding each folder open by path on Windows (`CreateFileW`) instead of `NtCreateFile`.* NTFS refuses to
    rename a folder while a handle below it is open (checked on this machine), but the safety would then rest on that
    rule of one file system; the relative open rests on nothing. .NET opens folders relative to a handle the same way
    in its recursive enumeration, and Rust's `remove_dir_all` deletes this way since CVE-2022-21658.
- **D4. Folders are listed by their path; only listing does.** The names come from `Directory` enumeration of the
  folder's path, and every open and remove goes through handles. A listing that a rename or a link swapped in made read
  another folder can only make the delete miss names, which then fails (the folder isn't empty: `IOException`), never
  delete outside the folder.
  - *Rejected: listing through the handle.* `readdir`'s `dirent` differs between glibc, musl and macOS (with
    `$INODE64` symbols on Intel Macs), and Windows would need `FILE_FULL_DIR_INFO` parsing: more native code for
    completeness under attack, not for safety.
- **D5. Errors as .NET's recursive delete gives them.** The walk goes on past an entry it can't delete and throws the
  first failure at the end; an entry gone meanwhile is skipped; access refused is `UnauthorizedAccessException`,
  anything else `IOException`, naming the provider path. Two differences, both fixes: on Windows a folder holding a
  junction is deleted (today `UnauthorizedAccessException`, from .NET's `DeleteVolumeMountPoint` on the junction), and
  where a folder still has entries after the walk (a file another process holds open on a file system without POSIX
  deletes, such as FAT or a network share) the delete throws `IOException` instead of returning true with the folder
  still there.
- **D6. The native constants per platform, and CI on each.** Picked once from `OperatingSystem` and
  `RuntimeInformation.ProcessArchitecture` (an x64 process emulated on Arm needs the x64 values, P7), as a table:

  | | Linux x64 | Linux Arm, Arm64 | macOS x64, Arm64 |
  |---|---|---|---|
  | `O_DIRECTORY` | 0x10000 | 0x4000 | 0x100000 |
  | `O_NOFOLLOW` | 0x20000 | 0x8000 | 0x100 |
  | `O_PATH` | 0x200000 | 0x200000 | none (`O_RDONLY`, 0) |
  | `O_CLOEXEC` | 0x80000 | 0x80000 | 0x1000000 |
  | `AT_REMOVEDIR` | 0x200 | 0x200 | 0x80 |
  | `ENOENT`, `EACCES`, `EPERM`, `ENOTDIR`, `EINVAL` | 2, 13, 1, 20, 22 | same | same |
  | `ELOOP`, `ENOTEMPTY` | 40, 39 | 40, 39 | 62, 66 |

  What each error means to the walk (N5): `ENOENT`, gone (skipped, or false at the start); `EACCES` and `EPERM`, refused
  (`UnauthorizedAccessException`); `ENOTDIR` and `ELOOP` from an open, not a folder (then `readlinkat`); `EINVAL` from
  `readlinkat`, not a link; `ENOTEMPTY`, not empty (`IOException`); anything else, `IOException` with the system's
  message. The Linux values were run on x64 and on Arm64 under emulation here. `open` and `openat` are declared with
  their fixed arguments only (two and three); `O_CREAT` is never set, so the variadic mode is never read. Anywhere else (another Linux
  architecture, another system) the delete is `Directory.Delete`, as today, and the docs say so. CI gains two jobs that
  build and run Physical's tests: macOS (`macos-latest`, Arm64) and Linux on Arm (`ubuntu-24.04-arm`). They are not
  required checks in the ruleset, but they are in `ci.yml`, whose success `release.yml` requires on the tagged commit:
  a red one blocks a release, as the Windows job does (P8).
- **D7. Only Windows' raw calls are left out of the coverage measure (P5).** CI measures coverage on Linux only, where
  Windows' calls can't run. So the seam between the walk and the system returns raw facts (a handle; the attributes and
  reparse tag; the system's error number), and offers both of Windows' deletes; everything that decides is shared code,
  run and covered on Linux: what an entry is, which error means what, when to fall back from the POSIX delete, and the
  table of D6 (a unit test pins which column each system and architecture picks, on any system), and the `\\?\` form
  of a path, for a drive, a drive's root and a share (N3). What stays unmeasured is `WindowsFolders`, the class that
  holds the `LibraryImport` declarations and the wrappers that marshal their arguments, about forty lines with no branch
  but the success test of each call, marked `[ExcludeFromCodeCoverage]` with the reason (`tests/coverage.runsettings`
  already honours it). The Windows job runs every line of it: a test switch makes
  Physical use the classic delete, which NTFS would otherwise never need.
  - *Rejected: measuring coverage on Windows too and merging line by line.* The gate keeps each assembly's best figure
    across reports; merging lines would change what the gate means for every assembly (Common's lines run by provider
    tests would count), and move it out of the Linux job and `release.yml`.
- **D8. Release 2027.1.1 (the maintainer's choice, 2026-10-13).** A patch: both changes are fixes. An rc first, as for
  2027.1.0, from the same commit. The approval of this plan covers approving the `nuget` environment for both tags.

## Design

### Appends (#65)

**Common, `AppendByRewriteAsync`.** A loop of at most five attempts:

1. Read the file's info; check the caller's conditions against it, as today.
2. Make the attempt's temp file: the file's content when it is one (read with `ReadFileCoreAsync`), then the caller's
   bytes: from the caller's stream while no temp file holds them, else from the previous temp file at the offset where
   they start (N1). Only a temp file that holds them replaces the previous one, which is then disposed, and its offset
   is remembered; one whose read of the file failed is disposed and the previous kept.
3. Rewrite from position 0, with `IfMatch` on the version read, or with `IfNotExists` where there was no file.

An unconditional append goes round again on `PreconditionFailedException` (the subtype included) from the rewrite, and
on `FileNotFoundException`, or an exception `IsNotFound` recognises (P2), from reading a file deleted since its info was
read. Nothing else is caught: an exception from the caller's stream, read in step 2 outside those catches, ends the
append. On the fifth conflict it throws D1's exception. The XML docs say so.

**Physical.** `UpdateFileCoreAsync`'s append runs the same loop around today's two paths. Each attempt looks at the path
again, as today's single attempt does: a folder there, whether a file is there, then `IsReplaceable` and the mode the
new file takes (R2). Its refusals come in today's order: a folder; the caller's `IfNotExists`; a file `IsReplaceable`
refuses; the caller's `IfMatch`, on that look's version (R1). The first attempt to pass them spools the caller's stream
(D2; a spool it may not create is reported for the file, as `CommitAsync` reports its temp file), before the file is
opened (S1); an existing file is then opened and the caller's `IfMatch` checked again on the opened handle's version, as
today. A refusal on any attempt ends the append; `IsReplaceable`'s not-found is no refusal but a retry signal (S1). The
loop retries only on Physical's own signals, raised as a private marker that it unwraps (P3):

- on an existing file, the version check before the rename (`Changed`) and a file deleted since the probe (`OpenRead`'s
  or `IsReplaceable`'s `FileNotFoundException` or `DirectoryNotFoundException`, N7, R2);
- on a missing file, the name taken meanwhile (`AlreadyExists` through `taken`).

The commit's write copies the rewound spool where it copies `contents` today, after the file's handle is read and
closed, so Windows still renames over a file nobody holds open. A folder that takes the name stays `IOException`. The
spool is the one temp file of the append that `TempCreated` doesn't report, so the tests stage their write from
`TempCreated`, which fires for each attempt's commit, and from a new internal hook, `Probed`, called after each
attempt's look at the path (a folder, a file) and before `IsReplaceable` (R2, S1).

**Azure Blob** is unchanged; its docs already say this. **The other providers** call `AppendByRewriteAsync`, so they
change with it; their docs and tests follow.

### The folder delete (#70)

`DeleteCoreAsync` keeps its probe: a file is deleted by path as today; a folder goes to `DeleteFolder`; nothing there
returns false. Where the walk can't run (D6), `DeleteFolder` is today's `Directory.Delete(path, recursive: true)`.

- **`FolderDelete`** (new file, internal, shared): the start (D3), the walk, what an entry is, the errors (D5), the
  fallback between Windows' deletes, the test hook `Opening`, and the seam to the system:
  - open a folder by its path, following links: a handle, or an error number;
  - open an entry in a folder without following a link: a handle, the facts of D3 (Windows: attributes and tag; Unix:
    whether it is a folder, and for a non-folder whether it is a link), or an error number;
  - remove an entry (Unix: by folder and name, as a folder or not; Windows: through its handle, with the POSIX
    delete or the classic one): 0 or an error number.
- **`UnixFolders`:** the seam through `open`, `openat`, `readlinkat`, `unlinkat` (`LibraryImport` from `libc`,
  `SetLastError`, as `link` is), with D6's table. An fd is a `SafeFileHandle`, which closes it.
- **`WindowsFolders`** (`[ExcludeFromCodeCoverage]`, D7): `CreateFileW` with `FILE_FLAG_BACKUP_SEMANTICS` for a folder by
  its path, given in the `\\?\` form that shared code builds (N3), so long paths and any name work; `NtCreateFile`
  relative to a folder's handle, with `RtlNtStatusToDosError` for its status;
  `GetFileInformationByHandleEx(FileAttributeTagInfo)`; `SetFileInformationByHandle` with either disposition class. Checked on this machine before planning: a junction is
  removed by handle and its target kept; a file open for reading with delete sharing loses its name at once; a
  read-only file is refused with access denied, as `DeleteFile` refuses it.
- **Seams for the tests:** `DeletesByHandle` (true where D6 says the walk runs; a test sets false to cover the
  fallback), `Opening`, the classic-delete switch (D7), and the seam itself, which a fake implements to drive what a
  disk can't stage: an entry that turns from a folder into a file between the listing and the open, a removal refused,
  a folder not empty, each Windows error that falls back and one that doesn't.

## Compatibility

No public or protected member is added, removed or renamed, and the configuration shape and the gateway are untouched.
Package validation against 2027.0.0 stays green.

- **#65, behaviour:** on Physical, S3, MinIO, Google Cloud Storage, Box, SharePoint and a third-party provider that
  calls `AppendByRewriteAsync`, an unconditional append that met a concurrent change or create now succeeds, after the
  other writer's content, where it threw `PreconditionFailedException` or `FileAlreadyExistsException`. It throws
  `PreconditionFailedException` only after five attempts. A caller that caught the exception to retry keeps working, and
  now rarely gets there; a caller that relied on an unconditional append failing to learn that someone else created the
  file should pass `IfNotExists`, as the docs say. One corner keeps 2027.1.0's answer (code review F2, G1): on Linux and
  macOS, Physical's append that loses a new name throws `FileAlreadyExistsException` while the file there is still
  empty, which it can't tell from one a rename is about to fill and would undo an append made to.
- **The Common API door (P1):** `AppendByRewriteAsync` is a protected helper of the base class, so it is inside the
  door. Its signature and its promise (a concurrent write is never lost) stay; what changes is that it retries where it
  threw. This plan reads that as a fix toward the door's own rule, one meaning across providers, which the difference
  broke, and so as a patch. The maintainer's agreement is posted on #65 with this plan's approval, as it was on #59 for
  2027.1; step 1's PR says so in its title ("one-way door: the Common API") and links it under One-way doors (N4).
- **#70, behaviour:** a Physical folder delete never goes into a link, as .NET intends today, now also when one is swapped
  in. Visible differences: on Windows, a folder holding a junction is deleted where it threw (D5); a folder that still
  has entries after the walk throws `IOException` where it returned true (D5); on macOS, the folder that holds the
  deleted folder, and with `RefuseLinks` every folder on the way, must be readable (Risks). The file delete is unchanged.
