# Codebase review, 2026-10-10

- **Scope:** the whole repo at `bdfecad`: 63 files, every project, the tests and the build files.
- **How:** `review-code` deep, kind `audit`, model opus.
  - 11 lenses, each its own agent: 102 raw findings, reconciled to 77.
  - Each blocker, major and sensitive finding faced a solo refuter; three voters judged the rest.
  - 79 agents in all. Every finding was confirmed; none was refuted.
- **What follows:** the findings feed the modernization plans under #3. The feature list and the proposed order of work
  are in [2026-10-10-roadmap.md](2026-10-10-roadmap.md).

## Verdict

The code works on the happy path. Behind it are three kinds of trouble.

1. **Path and data-integrity bugs on the write and read paths.** The S3 provider has two public members that skip Common's segment validation and root protection. One of them takes over ordinary `ReadFileAsync(string...)` calls on the concrete type.
2. **Providers that do not mean the same thing.** On several paths, a failed write or append loses data or leaves it half-written. The seven providers disagree on move, overwrite, missing files, folder info, download URL lifetime, stream position and `PhysicalPath`. That breaks the "one meaning across providers" door in many places.
3. **A dated stack.** The sync wrappers block on async code with no `ConfigureAwait`. There is no `CancellationToken` and no ranged read. The packages target net8.0, months before .NET 8 support ends. The AWS SDK V3 is out of support, Box.V2.Core is five major versions behind, and Azure.Identity is deprecated. Coverage is not configured or enforced, and the shared test suite has assertions that cannot fail and no cleanup after a failure.

None of this is a blocker. 32 findings are major.

What to fix first:
- **Credentials:** rotate the MinIO key pair that is still in the `ado` remote's history, then remove that remote (F9).
- **Root escape:** close the S3 escape from the root (F1, F2).
- **Data integrity:** stop the failed-write data loss (F3, F4, F5, F6) and bound the SharePoint retry recursion (F8).
- **Door decisions:** settle in an issue, before the one-pass modernization starts, the one-way-door questions it would otherwise trip over: CancellationToken and ranged reads as additive members (F16, F17, F35), the naming rule that would rename protected abstracts (F22), and keeping or dropping net8.0 (F72).

## Findings

Order: major (F1–F32), then minor (F33–F75), then nit (F76–F77). No blockers. Every finding has status **open**.

### F1. S3: public `ReadFileAsync(versionId, absolutePathSegments)` skips segment validation and the root, and hides the base overloads for string arguments
- **Severity:** major (security) · **Anchor:** `WriteableFileProviders.AmazonS3/WriteableAmazonS3FileProvider.cs:114`
- **Against:** REVIEW.md "Paths and the root folder"; lenses.md security (a path that escapes the root).
- **Problem:** The method passes `path(absolutePathSegments)` straight to `Client.GetObjectAsync`. It runs no `validateSegments`/`getReadableSegments` and adds no root prefix. C# drops base-class candidates when a derived method applies. On a variable typed `WriteableAmazonS3FileProvider`:
  - `ReadFileAsync("dir","file.txt")` reads bucket key `file.txt` as version `dir`, outside the root.
  - `ReadFileAsync("a/b.txt")` asks for the empty key, with the path sent as versionId.
  - An empty first segment plus `tenantB/secret.txt` reads another tenant's key.

  Calls through `IWriteableFileProvider` or the base type are not affected. No test covers it.
- **Fix:** Make read-path resolution protected in Common (for example `resolveReadableSegments`). That needs a Common release, because S3 builds against the published 2026.10.10.4. Then decide in an issue (public member, one-way door): add `ReadFileVersionAsync(string versionId, params string[] pathSegments)` and obsolete the old member, or remove it now. Pin the fix with a test on a concrete-typed provider: `ReadFileAsync("dir","file.txt")` must read `root/dir/file.txt`, and an empty or `..` segment must throw `ArgumentException`.
- **Status:** open
- **Verified:** Solo refuter. A scratch console project referencing the real AmazonS3 project (UseLocalCommon) recorded the binding through expression trees. Both calls bound to `ReadFileAsync(String, String[])`. Three of the four merged reports had reproduced the same binding independently.

### F2. S3: public `EnumerateObjects(absolutePathSegments, deep)` lists any prefix in the bucket, ignoring the root
- **Severity:** major (security) · **Anchor:** `WriteableFileProviders.AmazonS3/WriteableAmazonS3FileProvider.cs:65`
- **Against:** REVIEW.md "Paths and the root folder"; lenses.md security; lenses.md api-compatibility (public that should not be).
- **Problem:** The method sets `Prefix = dirPath(absolutePathSegments)` with no validation and no root prefix. `EnumerateObjects(new string[0], true)` lists the whole bucket. `getRelativeSegments` then strips the first N segments without checking that they are the root. With root `tenantA`, the key `tenantB/x` comes back as `["x"]`, and passing that back to the provider resolves to a different object.
- **Fix:** Take relative segments and resolve them through the same protected Common helper as F1, or make the method private: `getDirectoryContentsAsync` is its only caller. Either way it is a public-member change, so it goes to the maintainers in an issue. Add a test that a provider with a root cannot list keys outside it.
- **Status:** open
- **Verified:** Solo refuter, by reading the code. No S3 endpoint was available. The path has no branches, and grep finds no other caller and no test. Counterpoint the refuter weighed: `Options` (with the key) is public, so the impact is limited to consumers passing caller-controlled segments.

### F3. A failed overwrite leaves a truncated file on Physical and Azure; the other five keep the old content
- **Severity:** major · **Anchor:** `WriteableFileProviders.Physical/WriteablePhysicalFileProvider.cs:78`
- **Against:** REVIEW.md "Deleting, moving, overwriting"; AGENTS.md "One meaning across providers".
- **Problem:**
  - Physical opens `FileMode.Create`, which truncates the file before the first byte is copied.
  - Azure `OpenWriteAsync(overwrite: true)` replaces the blob with an empty one first. The class doc admits "a failed upload leaves a partial blob".
  - S3, GCS, MinIO, Box and SharePoint replace the object only when the upload completes.

  So a source stream that fails halfway destroys the old content on two providers and leaves it intact on five.
- **Fix:**
  - Physical: write to a temp file in the target folder, then `File.Move(temp, p, overwrite: true)`.
  - Azure: stage the new content before replacing the target. This touches the append-blob design, so the maintainers decide.
  - Add a TestBase test that overwrites from a stream that throws halfway and asserts the old content survives.
- **Status:** open
- **Verified:** Solo refuter. A scratch probe against the local Physical project overwrote a 5-byte file from a stream that throws on its second Read. Afterwards the file was 1 byte long. Azure was confirmed from source and the class doc.

### F4. Append-by-rewrite is implemented five ways, and the S3 and GCS versions upload a half-appended file when the source stream fails
- **Severity:** major · **Anchor:** `WriteableFileProviders.AmazonS3/WriteableAmazonS3FileProvider.cs:132`
- **Against:** simplicity lens; REVIEW.md "Deleting, moving, overwriting"; AGENTS.md "One meaning across providers".
- **Problem:** S3 (130-136) and GCS (151-159) append through `await using` on a writeable local stream. `LocalFileStream` uploads on every dispose, so when the caller's `contents` throws, the object is overwritten with the old content plus whatever was copied. MinIO spools to a temp file and puts it only on success. Box (`BoxUploadBuffer.CombineAsync`) and SharePoint (two branches) are separate implementations again. The result is five implementations with two different failure behaviours.
- **Fix:** Add one protected Common helper, for example `appendByRewriteAsync`. It spools the existing content and then `contents` into a temp file, and calls `updateFileAsync(..., Overwrite, ...)` only after both copies succeed. Use it in all five providers. Add a TestBase case where the appended stream throws halfway and the original content must be unchanged.
- **Status:** open
- **Verified:** Solo refuter. A scratch in-memory provider used the S3 append branch verbatim. The file started as "ORIGINAL"; after a source that throws after 7 bytes, it was "ORIGINALPARTIAL" with one upload, and the caller still got the IOException. Box and SharePoint were only read.

### F5. The Physical local stream writes to the real file in place, so `SkipReUploadOnDispose` does nothing there, and a read-only stream of a missing file throws on Physical only
- **Severity:** major · **Anchor:** `WriteableFileProviders.Physical/WriteablePhysicalFileProvider.cs:119`
- **Against:** AGENTS.md one-way doors (`LocalFileStream`, one meaning across providers); lenses.md sensitive areas (the local stream's write-back).
- **Problem:** Physical opens the target itself (`FileMode.OpenOrCreate, FileShare.None`), and its `OnLocalFileStreamDisposingAsync` is a no-op. The interface and `LocalFileStream` docs promise a local copy that is committed on dispose unless `SkipReUploadOnDispose` is set. On Physical:
  - writes reach the file immediately;
  - an abandoned stream still creates the file;
  - Skip does not undo anything.

  The other six use a temp copy. Separately, a read-only stream of a missing file throws `FileNotFoundException` on Physical only. That difference is documented (IWriteableFileProvider.cs:184) but still differs.
- **Fix:** Copy to a temp file in the same folder, and on dispose replace the target in one step unless Skip is set. Choose one behaviour for a read-only missing file on all seven providers (`FileNotFoundException` is the clearer one). Add TestBase tests for both. This needs a maintainer's yes (one-way-door type, data integrity).
- **Status:** open
- **Verified:** Solo refuter. A scratch app on Physical wrote [9] after `SetLength(0)` with Skip set, and the file kept "9". An abandoned stream created the file. Correction: "other readers see partial content" is wrong. `FileShare.None` makes other readers fail with an IOException instead.

### F6. Box and SharePoint rewind the caller's stream and upload from byte 0; the other providers upload from the current position
- **Severity:** major · **Anchor:** `WriteableFileProviders.Box/WriteableBoxFileProvider.cs:357`
- **Against:** AGENTS.md "One meaning across providers"; REVIEW.md "Deleting, moving, overwriting".
- **Problem:**
  - Box sets `fileStream.Position = 0` for a new file (356-357) and for a new version (393-394).
  - SharePoint Overwrite rewinds (637-638) and sizes the upload from `Length`.
  - Physical, Azure, MinIO, S3 (`AutoResetStreamPosition = false`) and GCS upload from the current position.
  - Box's own Append and its non-seekable path also copy from the current position, so Box's Overwrite and Append disagree.

  A caller who has read past a header, or forgot to rewind, stores different bytes on Box and SharePoint than on every other provider.
- **Fix:** Never seek the caller's stream. For seekable streams, upload `Length - Position` from the current position, or spool from there. Add a TestBase test that writes from a stream positioned mid-way.
- **Status:** open
- **Verified:** Solo refuter, by reading the code. The `Position = 0` assignments are unconditional. The GCS Overwrite path relies on the SDK's documented behaviour. Box and SharePoint need live accounts, so they were not run.

### F7. SharePoint silently removes a leading path prefix that matches `WorkFolderPath`, so a subfolder with the work folder's name cannot be reached
- **Severity:** major · **Anchor:** `WriteableFileProviders.SharePoint/SharePointPaths.cs:17`
- **Against:** AGENTS.md "One meaning across providers"; REVIEW.md "Paths and the root folder".
- **Problem:** `StripWorkFolder` drops leading segments that equal the work folder, case-insensitively. It applies to caller paths, not only to a duplicated root. With `WorkFolderPath` "Archive/Stale":
  - `Archive/Stale/x` and `x` resolve to the same item;
  - writing `Archive/Stale/x` lands at the work-folder root;
  - `DeleteAsync("Archive","Stale")` is refused as the provider root.

  With a one-segment work folder such as "Reports", `Reports/2026.csv` silently lands at `<work>/2026.csv`. The behaviour is intentional (commit df2c047) and pinned by tests. It is still a second root mechanism, and every other provider has one.
- **Fix:** Strip the work folder only from the configured `RootDirectorySegments`, never from caller segments, or fold `WorkFolderPath` into `RootDirectoryPath` at construction. Change the pinning tests. Callers who rely on the prefix would break, so the maintainers decide in an issue.
- **Status:** open
- **Verified:** Solo refuter. Ran `SharePointPathTests` (11 passed), which shows both paths hit `/items/work1:/wb:/children` and that the work folder is refused as root. The code paths were traced through every operation.

### F8. SharePoint: `updateFileAsync` retries `itemNotFound` by calling itself with no limit
- **Severity:** major · **Anchor:** `WriteableFileProviders.SharePoint/WriteableSharePointFileProvider.cs:648`
- **Against:** implementation lens (error handling, edge cases).
- **Problem:** The `itemNotFound` catch calls `createFolderHierarchyAsync` and then `updateFileAsync` again, with no bound. For a top-level file after the cached work folder has been deleted, the hierarchy call gets zero segments and does nothing, so the request fails the same way again and again.
  - **Large-file path:** loops on `createUploadSession` without end.
  - **Small-file path:** the first PUT disposes the caller's stream, so the retry throws `ObjectDisposedException` and hides the real error.
- **Fix:** Retry at most once, with a flag or a bounded loop. After that, surface the original `ODataError`, or a `DirectoryNotFoundException` that wraps it. Re-buffer or rewind the stream the PUT disposed, or keep the PUT from disposing it.
- **Status:** open
- **Verified:** Solo refuter. A temporary MSTest probe drove the real Kiota adapter through a fake handler that always answers 404. It saw 200 consecutive `createUploadSession` POSTs, stopped only by the handler; the small-file path stopped after one request with `ObjectDisposedException`. The probe was removed afterwards.

### F10. [owner call] MinIO connects over plain HTTP unless `UseSSL` is set
- **Severity:** major (security) · **Anchor:** `WriteableFileProviders.Minio/MinioFileProviderOptions.cs:23`
- **Against:** lenses.md security (bias fail-closed; configuration input).
- **Problem:** `public bool UseSSL { get; set; }` defaults to false and is passed on as `.WithSSL(options.UseSSL)`. Any configuration that leaves UseSSL out sends every file over HTTP. A network attacker can read the content and change responses. SigV4 protects the key, not the body.
- **Fix:** A choice for the maintainers, because the default is part of the stored configuration shape:
  - **(a) Default to https** (or make it `bool?` with null meaning https). This breaks stored configurations that point at HTTP endpoints, such as local MinIO or s3mock.
  - **(b) Keep false, but throw** unless UseSSL is set explicitly or the host is loopback. This breaks only configurations that never set it.

  Doing nothing leaves plaintext as the silent default.
- **Status:** open
- **Verified:** Solo refuter. Correction: UseSSL has existed since the first commit (c582d8b), so the affected configurations are all the ones that never set it, not ones "written before the property existed". Not tested: whether a scheme in `HostAndPort` switches the SDK to TLS.

### F11. Download URL lifetime: Azure silently caps it, Box and SharePoint ignore it, S3 and GCS throw past 7 days
- **Severity:** major (security) · **Anchor:** `WriteableFileProviders.Box/WriteableBoxFileProvider.cs:503`
- **Against:** REVIEW.md "Credentials and download URLs" (a URL lives exactly as long as the caller asked); AGENTS.md "One meaning across providers".
- **Problem:**
  - **Box** never reads `validity`; its URL is fixed at 15 minutes.
  - **SharePoint** returns Graph's `@microsoft.graph.downloadUrl`, which lives up to about an hour.
  - **Azure** caps validity at 7 days without saying so, and a test pins the cap.
  - **S3 and GCS** throw past 7 days, according to their SDK strings.
  - **Missing file:** Azure, S3 and GCS sign a URL anyway, while Box and SharePoint throw `FileNotFoundException`.

  A caller who asks for a 30-second link gets one that can leak for 15 to 60 minutes.
- **Fix:** Validate `validity` once in Common (greater than zero, at most the provider's maximum) and throw `ArgumentOutOfRangeException` the same way everywhere. For Box and SharePoint, the maintainers choose: throw `NotSupportedException`, or document validity as an upper bound and throw when the provider's fixed lifetime is longer. Decide whether a missing file throws everywhere or nowhere. Add a TestBase test.
- **Status:** open
- **Verified:** Solo refuter, by reading the code. The S3 and GCS behaviour past 7 days rests on SDK strings and was not run.

### F13. Sync-over-async bridges without `ConfigureAwait(false)`, and inconsistent exception unwrapping
- **Severity:** major · **Anchor:** `WriteableFileProviders.Common/WriteableFileProvider.cs:383`
- **Against:** REVIEW.md "Streams and I/O" (no blocking waits); lenses.md modernization; .editorconfig CA2007.
- **Problem:** Every sync member blocks on async code with no `ConfigureAwait(false)` anywhere in the libraries:
  - `RunTaskSerial` uses `.Result`/`.Wait()`; `GetDownloadUrl` and `Move` block directly (see F33); `LocalFileStream.Dispose` blocks too.
  - So `GetFileInfo`, `GetDirectoryContents` and `CreateReadStream` deadlock under a single-threaded SynchronizationContext (WinForms, WPF, classic ASP.NET).
  - The Box (`.Wait()`, line 50) and SharePoint (`GetAwaiter().GetResult()`, line 39) constructors block on network calls, so `WriteableFileProviderSerializer.FromConfiguration` does network I/O, and Box wraps auth errors in `AggregateException`.
- **Fix:**
  - Add `.ConfigureAwait(false)` to every library await and raise CA2007 to warning for the library projects.
  - Route every sync bridge through one `GetAwaiter().GetResult()` helper.
  - Move Box's token fetch and SharePoint's drive lookup into a lazily awaited init, keeping the single-options constructor the serializer needs.
  - Note in the PR that the exception type of a Common API member changes.
- **Status:** open
- **Verified:** Solo refuter. A .NET 10 file-based probe copied the patterns exactly. `RunTaskSerial` over `Task.Delay` on a non-pumping context printed "completed within 3s: False"; the `.Wait()` path threw `AggregateException` while `RunTaskSerial` threw `FileNotFoundException`.

### F14. The local stream copies the provider's download with a sync `CopyTo` inside an async method
- **Severity:** major · **Anchor:** `WriteableFileProviders.Common/WriteableFileProvider.cs:335`
- **Against:** REVIEW.md "Streams and I/O" (async all the way down); lenses.md modernization.
- **Problem:** `createLocalFileStreamAsync` runs `using (var fs = await readFileAsync(...)) fs.CopyTo(tempStream);` on a temp file opened without `FileOptions.Asynchronous`. Every non-Physical `CreateLocalFileStreamAsync`, and every S3 and GCS Append, blocks a pool thread for the whole download. Correction from the refuter: Azure Append does not use this path; it appends natively.
- **Fix:** Use `await using` and `await fs.CopyToAsync(tempStream)`, and open the temp file with `FileOptions.Asynchronous | DeleteOnClose`. Add a token when F16 lands.
- **Status:** open

### F15. `AzureFileStream` overrides no async read, so async reads from Azure run sync `Read` on the thread pool; the provider also uses the superseded `DownloadAsync`
- **Severity:** major · **Anchor:** `WriteableFileProviders.AzureBlob/AzureFileStream.cs:32`
- **Against:** REVIEW.md "Streams and I/O"; lenses.md modernization.
- **Problem:** Only `Read(byte[],int,int)` is overridden. `ReadAsync`, `Read(Span)` and `CopyToAsync` fall back to Stream's defaults, which run the sync network Read on pool threads. The stream comes from `DownloadAsync()`; Learn lists `DownloadStreamingAsync`/`DownloadContentAsync` as the current download APIs.
- **Fix:** Override `ReadAsync` (both overloads), `Read(Span<byte>)` and `CopyToAsync` to delegate to the inner stream. Switch to `DownloadStreamingAsync` (which also takes `Range`). Keep the public type and only add members (see F64 and F71).
- **Status:** open
- **Verified:** Solo refuter. A verbatim copy of the class around a counting probe stream: `CopyToAsync` made 3 sync reads and 0 async reads on pool threads. Correction: the Learn quote "as a replacement to this API" belongs to `DownloadContent`'s remarks, not to `DownloadAsync`'s.

### F16. No `CancellationToken` anywhere in the public or protected API
- **Severity:** major · **Anchor:** `WriteableFileProviders.Common/IWriteableFileProvider.cs:17`
- **Against:** lenses.md modernization; AGENTS.md one-way doors (Common API).
- **Problem:** No async member and no protected abstract takes a token. A 100 MB upload, a paged folder delete, or Azure's copy-poll loop in `move` (`Task.Delay(1000)` against a 10-minute timeout) cannot be cancelled, and `RequestAborted` cannot flow into them.
- **Fix:** Add tokens on new overloads, never by changing an existing signature:
  - default interface members that forward to the old ones;
  - protected virtual token-taking overloads on `WriteableFileProvider<T>` whose base forwards to the existing abstracts;
  - pass the token into every SDK call, `CopyToAsync` and `Task.Delay`.

  `params string[]` overloads need a non-params `string[]` form, because a token cannot follow `params`. This needs the maintainers' agreement. Raise CA1068 to warning afterwards.
- **Status:** open
- **Verified:** Solo refuter. Grep finds CancellationToken only in the test's fake handler.

### F17. Index-based (ranged) reads are missing from the Common API, although every SDK supports them
- **Severity:** major · **Anchor:** `WriteableFileProviders.Common/IWriteableFileProvider.cs:58`
- **Against:** maintainer request (index-based reads); lenses.md modernization; AGENTS.md one-way doors.
- **Problem:** No read overload takes an offset or a length.
  - Azure and S3 return non-seekable network streams.
  - MinIO, Box, GCS and SharePoint download the whole object to a temp file first (F65).
  - Only Physical can seek without a full transfer.

  Reading a slice of a large object therefore downloads all of it.
- **Fix:** Add a ranged read, for example `ReadFileAsync(string[] pathSegments, long offset, long? length, CancellationToken ct = default)`, implemented natively per provider: S3 `ByteRange`, Azure `BlobDownloadOptions.Range` or `OpenReadAsync`, GCS `Range`, MinIO `WithOffsetAndLength`, Box offsets, a Graph `Range` header, and `Seek` on Physical. Look up each SDK signature before coding. Add it as a default interface method or a base virtual (F35, F36), with the maintainers' agreement. Pin offset-past-end and length-0 behaviour in TestBase.
- **Status:** open
- **Verified:** Solo refuter. Correction: the MinIO, Box, GCS and SharePoint streams can seek, but only after a full download.

### F21. `IFileInfo.PhysicalPath` means a local disk path on Physical but a storage key or bare name elsewhere, and Box and SharePoint disagree with themselves
- **Severity:** major · **Anchor:** `WriteableFileProviders.Box/WriteableBoxFileProvider.cs:225`
