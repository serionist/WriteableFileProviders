# Final review of 2027.0.0, 2026-10-11

- **Scope:** the whole repo at `581e050`, label `2027-final`: 213 files, every project, the tests, the build files, the
  workflows and the docs.
- **How:** `review-code` deep, kind `audit`, model opus: 11 lenses, 34 agents. Each finding faced a solo refuter or
  three voters; 20 were confirmed (4 major, 16 minor) and none was refuted.
- **What follows:** the main session decided every finding under the maintainer's standing instruction ("do the
  recommended"; fail closed where it matters), recorded as D29 to D32 in
  [the modernization plan](../plans/2026-10-10-modernization.md). Two branches of #16 fixed them: `16-final-common`
  (Common, the build and release harness, the shared read stream, the error policy) and `16-final-providers` (the
  provider-specific findings). The decisions are at the end, under "Decisions".

The report below is as the audit wrote it.

## Verdict

This audit confirmed 20 findings in 2027-final: 4 major, 16 minor, no blockers. Every finding survived its refutation pass, and none was refuted. Most of the code holds to the 2027 contract. The problems sit where providers part ways, in paths, folders, listings, signed URLs and errors, where one member does something different on some stores, and in a few gaps between the docs, the plan and the release harness.

Fix these first:

1. **The Azure root escape (F1).** A root containing `.` or `..` sends reads, writes and deletes outside the root, and with a shared key into another container. Validate the root once in Common.
2. **The Physical/Windows trailing dot or space alias (F2).** It silently overwrites, or recursively deletes, a file or folder the path does not name.
3. **The plain-http `ServiceUrl` on AmazonS3 (F3).**
4. **Decisions on the seven open error-policy items (F4)**, recorded in the plan before the 2027.0.0 tag.

Two other decisions also have to be made before the tag because they touch the Common API one-way door: whether `CreateLocalFileStreamCoreAsync` stays virtual (F11), and the missing migration entry for calls with no path (F10). Several fixes change which paths or options are accepted, so the maintainers decide them.

## Findings

### F1. Azure Blob provider never validates its configured root, and a '.' or '..' root segment reaches blobs outside the root and outside the container
- **Severity:** major
- **Anchor:** `src/WriteableFileProviders.AzureBlob/WriteableAzureBlobFileProvider.cs:463`
- **Judged against:**
  - REVIEW.md "Paths and the root folder": no path reaches outside the provider's root.
  - lenses.md security: input from configuration trusted without validation, and a path that escapes the provider's root.
  - AGENTS.md One-way doors, "One meaning across providers": SharePoint validates its root, Azure does not.
- **Problem:**
  - `BlobName(path) => string.Join('/', path.AbsoluteSegments)` puts `Options.RootDirectorySegments` into the blob name unchecked.
  - Common's `Resolve` validates only the caller's segments, then returns `new ResolvedPath(Options.RootDirectorySegments, parts)` (WriteableFileProvider.Paths.cs:26).
  - `FileProviderOptions.RootDirectoryPath` only splits the value on '/'. Neither Azure constructor checks the root. SharePoint does, through `ValidateSegments(root)` (WriteableSharePointFileProvider.cs:268).
  - Azure.Storage.Blobs 12.30.1 normalizes dot segments in the blob URL:
    - A root of `tenants/../other` addresses `files/other/...`, another prefix in the same container.
    - A root of `../secrets` addresses a blob in another container, `secrets`.
  - Listings use the literal prefix, so they show nothing there and the escape goes unnoticed.
  - Exploiting it needs the root to come from untrusted input, such as a tenant id or a stored configuration row.
  - This finding absorbed a merged one: only SharePoint validates the root, and S3, MinIO, GCS and Box pass `RootDirectorySegments` through unchecked as well. AWSSDK.S3 sends the key literally and GCS escapes object names, so the concrete escape is Azure's.
- **Fix:**
  - Validate the root as SharePoint's `ResolveRoot` does (`ValidateSegments` plus `IsSegmentAllowed`) and throw `ArgumentException` naming `RootDirectoryPath`.
  - Preferably do this once in Common for every provider except Physical, whose root is an OS path by design. That also closes the parity gap.
  - Add options tests showing that roots with `.`, `..` and percent-encoded dot segments throw.
  - Record the change in docs/migration-2027.md under Azure Blob Storage, since a stored configuration with a dot-segment root will stop constructing.
- **Status:** open
- **Verified:** solo refuter, refutation failed. A scratch worktree at 581e050 ran a console app against the real AzureBlob project, using the shared-key `(options, BlobContainerClient)` constructor and a request-recording handler.
  - Root `tenants/../other` sent `HEAD` and `DELETE .../files/other/x.txt`.
  - Root `../secrets` sent `HEAD` and `DELETE https://acct.blob.core.windows.net/secrets/x.txt`.
  - Root `./x` sent `.../files/x/x.txt`.
  - Not verified: signed URLs (the probe failed on the faked 404 before signing), and the merged S3, GCS and Box part.

### F2. Physical on Windows treats a name ending in '.' or ' ' as the name without it, so it reads, overwrites or deletes a different file than the path names
- **Severity:** major
- **Anchor:** `src/WriteableFileProviders.Physical/WriteablePhysicalFileProvider.cs:379` (`IsSegmentAllowed` at :340)
- **Judged against:**
  - AGENTS.md One-way doors, "One meaning across providers".
  - REVIEW.md Paths and the root folder.
  - Plan D4 Paths/Listing (D27).
- **Problem:**
  - Common's `IsValidPart` refuses only parts that are empty, whitespace, all dots and spaces, or contain control characters (WriteableFileProvider.Paths.cs:107-108).
  - Physical's `IsSegmentAllowed` refuses only ':'.
  - `FullPath` passes the segments through `Path.GetFullPath`, which on Windows drops trailing dots and spaces. So:
    - `UpdateFileAsync("report.txt.")` overwrites `report.txt`.
    - `DeleteAsync("logs ")` reaches `Directory.Delete(fullPath, recursive: true)` on the folder `logs`.
  - On S3, Azure and GCS these are separate keys. Box refuses trailing spaces.
  - The test fixture already knows about the behaviour (PhysicalConformanceTests.cs:67-70) but only uses it to skip staging names. No doc or test covers it.
- **Fix:**
  - On Windows, refuse a segment ending in '.' or ' ' in `IsSegmentAllowed` with `ArgumentException`, as ':' is refused now. Alternatively, refuse it on every OS so paths stay portable.
  - Add a Windows CI test with `DeleteAsync("dir ")` and `UpdateFileAsync("a.txt.")` next to an existing `dir` and `a.txt`.
  - Document the rule in the provider remarks and the README.
  - The fix changes which paths are accepted, so the maintainers decide it.
- **Status:** open
- **Verified:** solo refuter, reproduced on Windows in a scratch worktree at 581e050.
  - `GetFileInfoAsync("report.txt.")` reported Exists=True with PhysicalPath `<root>\report.txt`.
  - `UpdateFileAsync("report.txt.", "REPLACED")` overwrote `report.txt`.
  - `DeleteAsync("logs ")` returned True and recursively deleted the real folder `logs` and its contents.
  - This was kept apart from F4 on purpose. F4's item 7 is the open policy decision; this is one concrete bug with its own test and docs fix.

### F3. AmazonS3 ServiceUrl accepts plain http to any host, which skips the D7 guard that MinIO and GCS enforce
- **Severity:** major
- **Anchor:** `src/WriteableFileProviders.AmazonS3/WriteableAmazonS3FileProvider.cs:189`
- **Judged against:**
  - Plan D7 "Safer defaults": plain HTTP to a host that is not loopback throws unless `AllowInsecureHttp`.
  - REVIEW.md "Credentials and download URLs".
  - AGENTS.md "One meaning across providers".
- **Problem:**
  - `SettingsFor` checks only that `ServiceUrl` is absolute and http or https. There is no loopback or `AllowInsecureHttp` check, and the options class has no `AllowInsecureHttp`.
  - MinIO refuses the same thing on the same S3Core (WriteableMinioFileProvider.cs:181-182), and so does GCS (:429).
  - S3Core then presigns for http (S3Core.Urls.cs:53). So `ServiceUrl = "http://minio.internal:9000"` sends file contents, session tokens and presigned bearer URLs in clear text, to a host the MinIO provider refuses.
  - `ServiceUrl` is new in 2027.0.0, so no stored configuration depends on the lenient behaviour.
  - SigV4 never sends the secret key, and the attacker needs a position on the network path, so this is not a blocker.
- **Fix:** owner call.
  - Add `AllowInsecureHttp` to `AmazonS3FileProviderOptions`, and throw `ArgumentException` in `SettingsFor` for an http `ServiceUrl` whose host is not loopback unless it is set. Use MinIO's message.
  - Add the options test, and the D7 line in the plan and in docs/migration-2027.md. The existing AmazonS3OfflineTests use `http://s3.test`, so they would have to opt in.
  - If the maintainers prefer Azure's line instead (refuse http only where a bearer token travels), say so in the `ServiceUrl` XML docs, so the difference from MinIO is a recorded decision.
- **Status:** open
- **Verified:** solo refuter. A probe test in a scratch worktree, with `ServiceUrl = "http://minio.internal:9000"` and an intercepting HTTP factory, built the provider without error. `GetSignedUrlAsync` returned `http://minio.internal:9000/bucket/root/f.txt?X-Amz-...`. Nothing in the plan, the migration guide or the XML docs records a choice to leave it open.

  - The Physical behaviour was run in a scratch worktree on Windows. With `a` holding "original", `GetFileInfoAsync("a.")` reported it with length 8, and `UpdateFileAsync("a.", "X")` overwrote `a`. Reserved-character names reported missing on read and threw `IOException` on write.

### F5. Object stores (S3, MinIO, Azure, GCS) write a file over an existing folder path instead of refusing it as the other providers do, so a listing then shows two entries with the same name
- **Severity:** minor
- **Anchor:** `src/Shared/S3/S3Core.Writes.cs:25`
- **Judged against:** AGENTS.md One-way doors, "One meaning across providers"; the implementation lens's duplicates edge case.
- **Problem:**
  - These refuse a write to a folder path with `IOException`, and their tests pin it:
    - InMemoryFileProvider.cs:135-136;
    - Physical (:219-220);
    - Box (Transfers.cs:45-46);
    - SharePoint (SharePointProviderTests.cs:446);
    - the base class's local stream (WriteableFileProvider.Core.cs:282).
  - These never check: `S3Core.WriteAsync`, Azure's `OverwriteAsync` (Writes.cs:41), GCS's `UpdateFileCoreAsync` (:193), and `AppendByRewriteAsync`.
  - With `dir/x.txt` present, `UpdateFileAsync("dir", ...)` creates the object `dir`. After that:
    - the listing shows both a folder `dir` and a file `dir`;
    - `GetFileInfo("dir")` reports a file;
    - `DeleteAsync("dir")` removes only the file.
  - No conformance test covers it.
  - S3BehaviourTests deliberately pins that a file and a folder of the same name can coexist on S3 when the file comes first. The InMemory provider also accepts the reverse order (line 139). The fix should account for both.
- **Fix:** decide one rule and pin it in ProviderConformanceTests (`Write_ToAFolderPathThrowsIOException`). Either:
  - have the object stores refuse, with a one-key listing of `path/` before the write (not atomic, one more request); or
  - record this as a store difference in D4 and the providers' docs. Listings would still show duplicate names.
- **Status:** open
- **Verified:** solo refuter. A probe test in a scratch worktree at 581e050 ran against the emulators.
  - **MinIO tests (both endpoints):** the write succeeded. Listings were `[D:dir, F:dir]` and `[F:dir]`, with `IsDirectory=False`.
  - **Same provider, local-stream route:** `CreateLocalFileStreamAsync("dir", readOnly:false)` threw `IOException`, so one provider is inconsistent between its two write routes.
  - **Azurite:** the write succeeded, with listing `[D:dir, F:dir]`.
  - **GCS:** not run. It was read only.

### F6. Azure range read returns the wrong bytes when offset + length overflows: the service ignores the malformed range and the whole blob is returned as if it were the range
- **Severity:** minor
- **Anchor:** `src/WriteableFileProviders.AzureBlob/WriteableAzureBlobFileProvider.cs:222`
- **Judged against:** D4 Reads (a ranged read returns the bytes asked for, and an over-long length reads to the end). S3 and GCS guard the same overflow, and their tests pin it (S3BehaviourTests.cs:210, GcsProviderTests.cs:494).
- **Problem:**
  - `new HttpRange(offset, length)` is sent as is, and the body is returned without checking for a 206.
  - Azure.Core 1.60.0 renders `(2, long.MaxValue)` as `bytes=2--9223372036854775808`.
  - Azurite 3.37.0 answers that with 200 and the whole blob, so `ReadRangeAsync("f.txt", 2, long.MaxValue)` returns "0123" where S3 and GCS return "23".
  - S3 (S3Core.Objects.cs:165) and GCS (:566) guard this case.
  - SharePoint builds the same unguarded header (Content.cs:93). There a 200 is skipped into correctly, but a 416 would read as empty.
  - Real Azure's answer to the malformed header is unverified.
- **Fix:**
  - Pass `length` only when `length <= long.MaxValue - offset`, otherwise use `new HttpRange(offset)`, as S3 and GCS do.
  - Apply the same guard in SharePoint's `DownloadAsync`.
  - Add the S3 test's four (offset, length) cases to the conformance suite.
- **Status:** open
- **Verified:** vote, 3 of 3 real. The malformed headers were reproduced with Azure.Core 1.60.0. The Azurite reply comes from the original finding and was not rerun by the voters. The missing guard and status check are shown in the source.

### F7. S3 and MinIO Create URLs are create-only only when the server honours If-None-Match, yet the provider offers them as native Create URLs on every endpoint
- **Severity:** minor
- **Anchor:** `src/WriteableFileProviders.Minio/WriteableMinioFileProvider.cs:125`
- **Judged against:**
  - `SignedUrlAccess.Create` ("Upload the file only if it does not exist yet").

- **Status:** open
- **Verified:** solo refuter, by reading the code and docs. No old or non-conforming server was run.

### F9. S3/MinIO recursive listing drops an addressable folder whose only keys sit under an unaddressable subfolder, although the one-level listing shows it
- **Severity:** minor
- **Anchor:** `src/Shared/S3/S3Core.Objects.cs:101`
- **Judged against:** D4 Listing ("EnumerateAsync(recursive: true) walks every level and yields each folder once"); the base class's default recursive walk and Azure's `EnumerateTreeAsync`, which list the folders above the first name that cannot be addressed.
- **Problem:**
  - `if (!folders.All(_isAddressable) || ...) continue;` skips the whole key, including its addressable ancestors.
  - For a bucket holding only `a/%2e%2e/x`:
    - the one-level listing yields folder `a` (lines 55-59 check only the prefix's own name), and `GetFileInfo("a")` says it is a folder;
    - the recursive listing never yields `a`.
  - Azure handles this on purpose (lines 382-391), and GCS uses the base walk, which yields `a`.
  - The conformance case `List_LeavesOutNamesThePathRulesRefuse` misses it, because `dir/ok.txt` always makes `dir` visible.
- **Fix:**
  - Yield the folders up to the first unaddressable segment (`Array.FindIndex(folders, f => !_isAddressable(f))`) before skipping the key, and yield the file only when every segment is addressable.
  - Add a conformance case with a folder that holds only an unaddressable subfolder, comparing the recursive and one-level listings.
- **Status:** open
- **Verified:** vote, 3 of 3 real, from the source. `IsAddressable` refuses `%2e%2e` because it decodes to `..`.

### F10. Calls with no path, such as GetDirectoryContentsAsync() for the root, no longer compile, and docs/migration-2027.md does not record it

### F11. CreateLocalFileStreamCoreAsync is a protected virtual extension point that third-party providers cannot implement, and it ships in 2027.0.0 as part of the Common API
- **Severity:** minor (lowered from major at verification)
- **Anchor:** `src/WriteableFileProviders.Common/WriteableFileProvider.Core.cs:275`
- **Judged against:** AGENTS.md One-way doors: The Common API (protected `...CoreAsync` members that third-party providers build on); lenses.md api-compatibility.
- **Problem:**
  - The member returns `LocalFileStream`, a `public sealed` class whose constructor is `internal`. Common's only InternalsVisibleTo is Common.Tests, so no other assembly can build one.

  Either way, add a Common.Tests case with a provider that overrides the member.
- **Status:** open
- **Verified:** solo refuter. In a scratch worktree, calling the constructor from the Physical project failed with CS1729. Severity was lowered because nothing is wrong at run time, an override can still check, log or delegate to base, and only option (a) has to be decided before the tag.

  - `Write_IfMatch` never reaches Graph with a stale ETag, because `SupportsAtomicPreconditions => false` makes the base class pre-check and throw first.

- **Verified:** solo refuter, by reading the code path through `UpdateWithPreconditionsAsync` (Core.cs:414-420) and `AppendByRewriteAsync` (Core.cs:345-375). Nothing was run, because only a live Graph account can answer the question.

### F15. The S3/MinIO signed-URL expiry test assumes the host and container clocks agree within 1.5 seconds
- **Severity:** minor
- **Anchor:** `tests/Shared/S3/S3BehaviourTests.cs:631`
- **Judged against:** lenses.md tests (deterministic, no clock dependence); REVIEW.md Always 1.
- **Problem:**
  - The test signs with a 1 s validity, waits 2.5 s, then asserts 403.
  - X-Amz-Date comes from the host clock, but MinIO judges expiry on the container's clock with no tolerance.
  - The SDK corrects its clock only after a skew error measured in minutes.
  - If the container clock lags by more than about 1.5 s (up to about 2.5 s counting the truncation of X-Amz-Date), the URL is still accepted and the test fails with no product bug. A WSL2/Docker Desktop VM after host sleep is the likely case.
  - CI's Linux runner shares the kernel clock, so the exposure is local Windows runs.
  - GcsLiveTests.cs:212 has the same shape but is less exposed.
- **Fix:** read the server's time from a response's Date header, then poll with a bounded deadline until the server's Date is past X-Amz-Date + X-Amz-Expires, and only then assert 403. Keep the assertion strict.
- **Status:** open
- **Verified:** solo refuter, by reading the code. In this session, Docker on this machine was within about a second of the host clock, which shows the drift is conditional, not absent. The suite was not run, because in-sync clocks would only show a pass.

### F18. Box chunked upload allocates a new part-size buffer on every upload, where the Azure and S3 paths rent theirs from ArrayPool
